# Chany Video Assembly

Turn accepted clips into a measured, reproducible deliverable. Sequencing comes from the approved shot plan, target specifications come from the user or a current authoritative delivery source, and text comes from the approved copy lock.

Read [references/assembly-contract.md](references/assembly-contract.md) for the manifest, normalization, variant, verification, and performance-record contracts.

When a platform or placement is named, read and apply the shared [platform publication adapter](../chany-studio/references/platform-publication-adapter.md) to resolve current delivery requirements. Route the exact final render to `chany-publication-review` whenever claims, offers, rights, disclosures, industry rules, or platform release gates apply. Assembly itself never uploads, publishes, activates, or spends.

## Workflow

1. Run the environment check through `chany-preflight` before the first assembly in a runtime or after a missing-tool failure. Check only the tools needed for the requested operation. If that skill cannot be invoked separately, perform the same non-destructive checks without persistent project changes; do not install anything as an implied part of assembly. `ffprobe` is required for this workflow: if it is missing, blocked, or not observable, stop before writing media even when `ffmpeg` is present. If the runtime cannot expose a shell, the source files, or a writable output location, mark the capability `not_observable`, state that assembly did not run, and return the manifest and command plan instead of calling the tools missing.
2. Resolve the exact encode selections—ratio and pixel size, frame rate, video codec and pixel format, and audio layout—from the user's delivery specification or a current authoritative platform source. Record compliance constraints such as maximum duration, maximum file size, safe area, and allowed ranges separately. The output duration comes from the accepted shot-plan in/out points and may proceed when it satisfies an authoritative maximum; a maximum is not another exact duration to choose. If a required encode selection remains unresolved, stop at the manifest and ask the user to select it instead of substituting a remembered platform default. An unresolved hard platform requirement keeps publication blocked.
3. Build a clip manifest from the approved `chany-ugc-ads` shot plan. Record a stable clip version or hash, path, in-point, duration, `usp_role`, and `message_rank`. Keep the accepted scene order and do not introduce a new message or transition.
4. Probe every input before writing output. Record actual dimensions, frame rate, duration, codecs, pixel format, time base, and audio-stream presence. If an input cannot be measured, name it and stop rather than silently encoding around it.
5. Normalize each clip to the one approved target. Scale to cover and crop without stretching, warn about meaningful content loss, make codecs and time bases consistent, and add a silent track in the target layout when an accepted clip has no audio.
6. Inspect every proposed intermediate and output path before running a command. Use fail-on-existing/no-clobber behavior by default (`ffmpeg -n` when using FFmpeg) and write each result to a new revision path. On collision, select a new version suffix or obtain explicit approval for that exact replacement; never use blanket overwrite such as `-y` without it. Never overwrite source clips or an accepted master.
7. When variants are requested, change exactly one approved property across the set. For hook-only variants, use the approved hook strings and keep the cut, timing, typography, position, audio, grade, and export settings identical. Burn text into pixels only when the user requests self-contained files and `chany-preflight` has verified that the selected font renders every code point in the exact approved strings. Do not silently substitute a fallback font; missing glyphs block burn-in until the user approves another verified font or a non-burned subtitle deliverable.
8. Probe every final file and report its actual width, height, frame rate, duration, codecs, and audio presence. Inspect an extracted frame for any burned text, store the verified render and source clip versions in the shared campaign state's assembly manifest when one exists, and run the applicable campaign and publication QA; a successful command alone is not delivery proof.
9. Write one performance-table row per output with result fields empty. Performance data is entered only after delivery, and any interpretation remains a hypothesis until tracking quality and sample sufficiency are checked.

Do not generate new footage, rewrite the script, invent hook copy, add music, extend duration, change clip order, or conceal a failed probe.

When assembly runs, record the commands or equivalent settings that actually executed and keep them distinct from any proposed handoff. When a required local tool is unavailable, return the completed manifest, the unblocking instruction supported by the observed environment, and the work that remains possible without that tool. If every source path and required target selection is resolved, add exact probe, normalization, and assembly commands with safely quoted paths and no-clobber behavior under a visible `NOT EXECUTED — handoff command plan` label. Otherwise return a clearly labeled command template whose unresolved values remain placeholders. When the operating system, package manager, or execution surface is not observable, provide only a diagnostic command for the user to run and request its result, or write `해결안: none pending observation`; never guess an installation command.
