# Free Pinterest discovery in Work

Use the host's included search and browser capabilities. A connected Apify account does not authorize paid Pinterest research. When the user requests free search, do not run any paid Actor, start a trial, subscribe, or switch to another source. Do not upload the product image to a search service: classify it locally and search the category only.

## Search transport, not another source

1. Read the taxonomy and run the exact L1 category with `domains: ["pinterest.com"]` on the available image-search tool.
2. If this returns no usable pins, try the **same category plus the provider word `Pinterest`**, without the failing domain parameter. This is a bounded transport fallback, not permission to use general-web images. Example: `Cosmetic Photography Pinterest`. Do not add brands, moods, lighting or other creative modifiers. Keep only paired public Pin-page URLs and `i.pinimg.com` images; discard all other results before opening, fetching, displaying or using them. Never present retailer or portfolio images as Pinterest references.
3. If needed, run the one taxonomy-approved direct L2 plus `Pinterest`, e.g. `Serum Photography Pinterest`. Request enough results within the live tool's supported limit; do not invent unsupported count/pagination arguments. Deduplicate Pins and duplicate image assets. A Pin page whose path contains a slug followed by a numeric ID is valid; retain the actually returned URL and do not invent a different Pin.
4. If the host exposes a browser, use Pinterest's visible search UI for the same category to inspect additional pins and their paired images. Use only the browser and capabilities actually exposed **in that Work conversation**. A parent's logged-in Chrome session is not evidence that Work Cloud can use it. Do not copy cookies, use hidden endpoints, automate login, bypass a challenge or scrape a feed. Browser search counts within the same six-discovery-call ceiling.

After two consecutive no-progress calls on one search transport, stop repeating that transport. One transition to the documented free fallback is allowed within the **same total maximum of six discovery calls**, then stop after two more consecutive no-progress calls or an explicit access-control block. Do not rotate hosts/proxies or repeat a blocked URL. A generic image-index empty result is different from Pinterest denying access. If a board page returns 403, stop that page route; a search-returned public preview can still be considered with the evidence limits below.

## Evidence and display

- Diagnose discovery, image retrieval, user-visible display, and model-visible inspection separately. A `web.open` 403 for an image URL proves only that this retrieval route failed; it does not identify whether Pinterest or the host caused the failure, or prove that native display also fails. Do not repeat the blocked route.
- A host-native image widget may perform its own new search. Read its current instructions and supported arguments before use; count that search within the same discovery ceiling. Do not assume it accepts previously returned image URLs, supports a domain filter, returns results to the model, or can supply the selected image to generation. A provider word in the query does not guarantee Pinterest provenance. If an asynchronous widget cannot expose and filter sources before display, it is not a verified Pinterest-only board and must not replace one. Do not infer visual inspection from a widget placeholder or infer a selected generation input from an on-screen image alone.
- Require a search/browser result that pairs the actual Pin page and actual image URL. Retain that association, number, query and provenance method. Do not manufacture image URLs from a Pin ID.
- A Pin page failing to open in the host does not prove that its independently returned public preview is inaccessible. If the host can show that preview, label `Pin page unverified; search-paired preview visually checked`. Do not call the page opened or independently verified. Reject orphan images with no paired Pin URL.
- Display actual images through the host's native image results, supported inline embeds or an allowed preview connector. Keep six as the target; fewer visible images means an incomplete board, never silently substitute a different provider. Do not download media to circumvent a host's presentation restriction. A selected image may be imported through the supported generation-input path after its source/use is disclosed and authorized.
- Preserve displayed numbering, the selected image and its Pin provenance through generation. Keep unselected images out of the generation request where supported.

On 2026-11-18 the development host's included image search returned zero results with a strict domain/site restriction, but provider-word queries returned some paired Pinterest images among unrelated results. This observation motivates the fallback; it is **not proof of six usable images or a successful new Work conversation**. Report actual visible/requested/missing counts in each execution.

For mixed search results, the offline [candidate filter](../../chany-reference-board/scripts/pinterest-candidates.mjs) helper accepts `{target_count, results: [{source_url, preview_image_url, paired_in_result, title, query}]}` with paired URLs copied from actual results. It filters domains and duplicates and strips outbound fields; it does not fetch or display images, establish rights or mark a board complete. Apply the same checks directly when the helper runtime is unavailable.
